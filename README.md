# APSRTC live bus tracker

A static web page that shows APSRTC buses moving live on a map. Pick a town, and it shows every tracked bus leaving that town (blue) or heading to it (orange), updating every few seconds.

This README records how the tracker was built: how the official site's data was decoded, what the APIs return, the mistakes made along the way, and how the web app works.

> **Personal use only.** The app uses keys read out of the official APSRTC web app. Anyone who can open `web/config.js` can see them. Don't commit `config.js` to a public repo or post the site publicly. APSRTC can change or revoke the keys at any time, which would break the app.

## Running it

The app has no backend. The browser does everything: it builds the encrypted query, calls the APSRTC API, and reads live GPS from Firestore.

**On your computer:**

```bash
cd web
python3 -m http.server 8777
# open http://localhost:8777
```

The Python command is just a file server. Any static file server works.

**On your phone or another computer:** put the four files in `web/` on any static host (GitHub Pages, Netlify, Cloudflare Pages) and open the URL. This works because:

- the APSRTC API sends `access-control-allow-origin: *`, so a page on any site may call it;
- Firestore's REST API accepts browser calls with the web API key;
- the host serves over HTTPS, so there's no mixed-content blocking.

Opening `index.html` straight from disk (`file://`) usually works in desktop browsers. Phone browsers usually block those cross-site calls, so use a host instead.

## How the official site works

The official tracker is <https://apsrtclivetrack.com>. It's a **Flutter web app** compiled to one large JavaScript file, `main.dart.js` (about 4.8 MB).

We inspected it through Chrome DevTools Protocol (CDP) on a local Chrome with remote debugging on port 9222, and by downloading `main.dart.js` and searching it.

It talks to two backends:

| Backend | Used for |
|---|---|
| `https://utsappapicached01.apsrtconline.in/uts-vts-api` | Schedules, places, service numbers (a cached read API) |
| Firestore, project `apsrtc-uts-prod` | Live GPS for each trip (`trackingDetailsV2`) and trip metadata (`serviceDetails`) |

The app reads each bus's tracking document with a one-shot `get()`. It polls; it doesn't use Firestore realtime listeners for buses.

### Browser storage

The official app keeps 12 IndexedDB databases. Most are empty between sessions:

| Database | Rows | Holds |
|---|---|---|
| `placesbox` | 12,593 | Offline copy of the place list (the search autocomplete) |
| `services`, `servicenumber`, `vehiclenumber` | 0 | Lookup caches |
| `favroute`, `favvehiclenumber`, `recentsearchbox`, `notificationdatabox` | 0 | User favourites, history, notifications |
| `firebase_remote_config` | 7 | Remote config values |
| `firebase-installations-database` | 2 | Firebase installation ID |
| `firebase-heartbeat-database` | 2 | SDK telemetry |
| `firebaseLocalStorageDb` | 0 | Firebase Auth. Empty: the app doesn't sign users in |

`localStorage` only holds `flutter.placesVersion` (448 at the time) and an empty `GetStorage`.

## The encrypted `q` parameter

Requests such as `/services/all?q=ATW-4x2h…` carry an encrypted, compressed JSON payload. The encoder is the `Ae` method of class `FJ` in `main.dart.js`. `web/app.js` has the same logic in `encodeQ()`.

**Steps:**

1. Start from the request object. Remove `userId` (it's sent as a header instead) and any `null` fields.
2. Turn it into JSON.
3. Compress with **raw deflate** (no zlib header), level 9.
4. Encrypt with **AES-256-GCM**, a random 12-byte nonce, and no additional data. The 32-byte key is hardcoded in the bundle and copied into `config.js` as `Q_KEY_B64`.
5. Assemble the bytes: `0x01` (version) + nonce (12 bytes) + ciphertext + GCM tag (16 bytes).
6. Encode as base64url and strip the `=` padding. The app refuses tokens over 1,900 characters.

**Example.** The URL we started from decodes to:

```json
{"sourceLinkId":13071,"destinationLinkId":2741,"sourcePlaceId":13071,"destinationPlaceId":2741}
```

That's a Repalle (13071) → Chirala (2741) search.

**Browser version.** `CompressionStream("deflate-raw")` does the compression and `crypto.subtle` does AES-GCM. `crypto.subtle` appends the tag to the ciphertext, which matches the layout above.

## API reference

Base URL: `https://utsappapicached01.apsrtconline.in/uts-vts-api`

**Headers on every request** (values are in `config.js`):

- `userId: 1363789069449`. This is a constant written into the official bundle, not a per-user login.
- `x-api-key: …`

Without `userId` the server replies `400 missing required header 'userId'`.

| Endpoint | Input | Returns |
|---|---|---|
| `GET /services/all?q=` | `{sourceLinkId, destinationLinkId, sourcePlaceId, destinationPlaceId}` | Today's trips between two places |
| `GET /nearby-services/upcoming?q=` | `{userLocation:{latitude,longitude}, destination:{placeId, linkPlaceId, placeName}}` | The next few departures at a stop and nearby stops. Only a short time window, not the whole day |
| `GET /mappedplaces/fetchAllUniquePlaces` | — | All places (~12,600): `placeId`, `placeName`, `linkPlaceId`, `mandalName`, `district`, `latitude`, `longitude` |
| `GET /servicesnumbers/all` | — | Every tracked trip today (~2,950): `oprsNo` + `serviceDocId` |
| `GET /starttrip/getallvehicles` | — | The fleet: `vehicleNumber` + `serviceType`. No routes |
| `GET /servicewaypointdetails/bydocid?q=` | trip id | Stop list for one trip |
| `GET /servicewaypointdetails/bydocid/history?q=` | trip id | Last week's arrival punctuality |
| `GET /appconfig?param=…` | e.g. `mappedPlaces` | Version numbers only |

### `services/all` response

Each trip looks like this (trimmed):

```json
{
  "oprsNo": "CL12/1", "serviceId": 1437000110692, "tripNo": 1,
  "serviceDocId": "22112026_CL12_1_REPALLE",
  "serviceType": "PALLEVELUGU", "depotName": "REPALLE",
  "serviceStartTime": "10:30", "serviceEndTime": "13:00",
  "startCityPlaceId": 13071, "endCityPlaceId": 2741,
  "sourceName": "REPALLE", "destinationName": "CHIRALA",
  "isCancel": false, "isDirect": false, "exactMatch": true
}
```

Things to know:

- **There is no "all buses from town X" endpoint.** Searches are always from → to, so the app sweeps many destinations (see [Schedule sweep](#1-schedule-sweep)).
- **Wildcards don't work.** A destination of `*` or `%` is not a pattern. The field is a numeric ID.
- **Times are for the stops you searched.** `serviceStartTime` is when the bus leaves your search's source and `serviceEndTime` when it reaches your destination. They are not the start and end of the whole route.
- **The trip ID ends in the depot.** In `serviceDocId` (`DDMMYYYY_<code>_<trip>_<DEPOT>`), the last part is the operating depot, not the destination.

## Firestore live tracking

| | |
|---|---|
| Project | `apsrtc-uts-prod` |
| Live GPS | `trackingDetailsV2/{serviceDocId}` |
| Trip metadata | `serviceDetails/{serviceDocId}` |
| Auth | Web API key only (`FS_KEY` in `config.js`) |

The REST endpoint is `https://firestore.googleapis.com/v1/projects/apsrtc-uts-prod/databases/(default)/documents/…?key=…`.

**Fields in a tracking document** (read on 22 Nov 2026):

| Field | Meaning |
|---|---|
| `latitude`, `longitude` | Last position |
| **`locationTime`**, `refreshedAt` | **Time of the last GPS ping**, in epoch milliseconds. This is how you tell whether a bus is live |
| `speed` | km/h, as a string |
| `locationBearing` | Heading in degrees |
| `busNumber`, `vehicleNumber` | Registration, e.g. `AP39UG2499` |
| `oprsNo`, `dcp`, `tripNumber`, `serviceId` | Trip identity |
| `depotName`, `depotId`, `driverName`, `dutyId` | Operations |
| `isOnline` | `"1"`, but **it stays `"1"` after the trip ends**. Don't use it |
| `ttl`, `expireAt` | When the document **expires** (about 2 days ahead). Not a last-update time |

> `apsrtc_track.py` assumes `locationSpeed` and treats `ttl` as "last update". Both assumptions are wrong for this data. Use `speed` and `locationTime`.

**Reading many documents at once.** `POST …/documents:batchGet?key=…` with a body like:

```json
{"documents": ["projects/apsrtc-uts-prod/databases/(default)/documents/trackingDetailsV2/<id>", "…"],
 "mask": {"fieldPaths": ["latitude", "longitude", "locationTime"]}}
```

- Results come back **out of order**, so match them by document name.
- Missing documents come back as `{"missing": name}`.
- IDs that contain spaces (e.g. `…_JANGAREDDY GUDEM`) work fine.

## Mistakes we made (and fixed)

| What we got wrong | What was actually happening | The fix |
|---|---|---|
| Encoded payloads were rejected (`not valid deflate data`) | The server wants **raw** deflate. We had used zlib-wrapped deflate | `deflate-raw` |
| Every request failed with `missing required header 'userId'` | `userId` is a header, not part of the payload | Send `userId` and `x-api-key` headers |
| "Arriving" buses always showed 0 | Both legs of a round trip share **one `serviceId`** (e.g. `OE18/3` out and `OE18/4` back). We de-duplicated by `serviceId`, which deleted every arriving trip | Key trips by **`serviceDocId`**. Label direction by `startCityPlaceId` / `endCityPlaceId` |
| Far too many buses counted as live (431 for Chirala) | Tracking documents keep their last position after the trip ends, and `isOnline` stays `"1"` | A bus is live only if `locationTime` is under **10 minutes** old |
| Only polling buses inside their timetable window | Times are per stop, so long routes go live hours "early". About half of Vijayawada's live buses were outside their window | The first pass checks every trip. Later passes use a wide window (6 h before, 90 min after) |
| One request per bus, every cycle | Hundreds of requests per cycle | `batchGet` with a field mask |

## How the web app works

### 1. Schedule sweep

Runs once when you pick a town (`sweep()` in `app.js`).

1. **Pick destinations to search.** From `places.js`, take the 18 nearest mandal headquarters within 45 km, plus the 30 nearest depot towns within 160 km. In `places.js`, flag 1 means the place name equals its mandal name; flag 2 means it's a depot town.
2. **Search both ways.** Call `services/all` for town → destination and destination → town, 8 requests at a time.
3. **Keep the right trips.** Keep trips where `startCityPlaceId` is the town (departing, blue) or `endCityPlaceId` is the town (arriving, orange). Key each trip by `serviceDocId`.
4. **Cache.** The result is saved in `sessionStorage` for 15 minutes, so picking the same town again is instant.

### 2. Live-position engine

All live data comes from Firestore `batchGet` requests, up to 100 trips each and 4 in parallel, with a field mask so only the needed fields come back.

| Tier | Which trips | How often |
|---|---|---|
| **View** | Live buses inside the visible map, enlarged by 25% | 5 s |
| **Off** | Live buses elsewhere | 20 s |
| **Pending** | Trips not live yet, within 6 h before their time and 90 min after | 60 s. This is how new departures are caught |

The rules behind the tiers:

- **First pass:** when a town is picked, every trip is checked once.
- **Pan or zoom:** the View tier runs again 250 ms after the map stops moving. If it's already running, it runs again as soon as it finishes.
- **No overlaps:** each tier schedules its next run only after the current one finishes.
- **Hidden tab:** all polling pauses, and everything refreshes as soon as you come back.
- **Town switch:** requests still in flight are cancelled (`AbortController`).

### 3. Start and stop events

When a trip goes from not-live to live, that's a departure. Its marker pulses for about 9 seconds and a line goes into the **Live activity** feed. When a live bus stops pinging, its marker is removed and the feed logs that it ended.

### 4. Map

- Leaflet with OpenStreetMap tiles and the **canvas renderer** (`preferCanvas`), which handles many moving markers better than individual DOM elements.
- Markers are created once and then only moved or restyled.
- Movement is smoothed between updates by one `requestAnimationFrame` loop. The loop runs only while something is moving or pulsing. Buses off screen jump straight to their new position.
- Click a bus to see its service number, type, direction, route, registration, speed, depot, scheduled departure and last GPS time.

## Configuration

All settings live in `web/config.js`.

| Setting | Default | Meaning |
|---|---|---|
| `HQ_RADIUS_KM` / `HQ_CAP` | 45 / 18 | Nearby mandal HQs to search |
| `DEPOT_RADIUS_KM` / `DEPOT_CAP` | 160 / 30 | Depot towns to search (long routes) |
| `SWEEP_CONCURRENCY` | 8 | Schedule requests in parallel |
| `SWEEP_CACHE_MIN` | 15 | Minutes to reuse a town's sweep |
| `VIEW_MS` | 5000 | Refresh for on-screen live buses |
| `OFFVIEW_MS` | 20000 | Refresh for off-screen live buses |
| `SLOW_MS` | 60000 | Refresh for trips not live yet |
| `VIEW_PAD` | 0.25 | How much to enlarge the visible area |
| `BATCH_SIZE` / `BATCH_PARALLEL` | 100 / 4 | Firestore batching |
| `FRESH_MIN` | 10 | Minutes since the last ping for a bus to count as live |
| `DONE_GRACE_MIN` | 90 | Stop checking a non-live trip this long after its end time |
| `PRESTART_MIN` | 360 | Start checking a trip this long before its time |
| `ANIM_MS` | 1500 | Marker glide time |

## Known limits and what's not verified

- **The new live engine hasn't been tested end to end.** That's the tiers, pan refresh, hidden-tab pause and town switch. `app.js` passes a syntax check and batching was measured on live data, but a full run of the page was never completed.
- **The sweep can miss buses.** Only the chosen nearby and depot towns are searched, so a bus arriving from a far town we didn't search won't show.
- **Big hubs are heavy.** Vijayawada has 6,000+ trips, which means a long first pass and many reads.
- **"Live" uses a 10-minute rule we chose.** The official app's own cut-off isn't known.
- **No seat or occupancy data.** The API doesn't provide it.
- **The keys are exposed.** Anything served from `web/` shows the keys to anyone who opens it. Making it public safely needs a small proxy that keeps the keys server-side and caches results.
